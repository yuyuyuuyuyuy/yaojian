我为什么这样做

我运营着一个日韩代购私人群。每一单要经历七个环节：收集表下单、海外平台下单、追商家物流、仓库快照核对、选国际物流、盯海关、国内分包发货。国际运输要手工对比多家物流商细则，物流状态要刷多个网站查询，群友催问要翻记录回复——痛点不是想出来的，是每天在发生的。

问题被拆成两类：能规则化的（查价、追物流、状态记录）交给系统；必须人做的（下单、核对、拍板）保留给人。这就是整个系统的原点。

第一步不是写功能，是建模型：订单状态机（待下单→已下单→已到仓→已发国际→已到国内→已发国内→已签收，异议则进售后），并设计了三处签收自动联动——包裹轨迹出现「已签收」，订单状态自动推进。最琐碎的状态维护被完全自动化，人只处理例外。

系统拆成 8 个 Agent：1 个主控（统一调度、运行日志）+ 7 个专职（订单解析、用户台账、国际物流选择、物流追踪、快照分拣、用户确认&售后、国内分包）。设计原则只有三条：职责单一（一个 Agent 只做一类事，出错好定位）；失败隔离（一个环节失败不阻塞整条流程）；数据库共享状态（Agent 之间不互相传话，一切可回溯）。

哪些环节交给 AI，是我最谨慎的决策：商品核对保留人工——AI 只识别快照上的运单号并分拣到用户（快照分拣Agent），「东西对不对」由群友看图人工确认，规避视觉误判风险；物流选线 AI 推荐 + 人工拍板（价格之外的因素人判断）；话术 AI 生成 + 人工转发（不碰个人号自动化红线）。

这个边界不是一步想对的：初版设计了「商品图 zip 自动匹配 + AI 视觉核对」，被真实使用否决——导出压缩包太麻烦、且核对结果必须人说了算。当天就重构为人工核对 + AI 分拣，一个被真实使用推翻的方案，比闭门造出的完美方案更接近真相。

国际物流选线是全系统最重的决策，我做了三件事：①克重区间方案矩阵——打包后克重与入库时差异大，单点估价不可靠，就按区间切档（≤2kg 按 0.5kg），每档给主选+备选，价格按区间上限保守估算；②合寄 vs 分寄枚举优化——枚举全部商品分组方式，把禁运词、数量上限、免税额度（书10本/CD20盘，超额按13%估税）作为约束和成本参与计算，分寄更省自动提醒；③净重估算链——入库克重扣 15% 外包装估净重，再加回新包装估重，最终按 ±10% 区间分析。

七条线路 779 个价格档位全部从官方 API 抓取入库，规则文本可维护可更新。

按 P0~P6 六阶段推进，每个阶段验收通过才做下一阶段：导入与解析→台账→物流选择→物流追踪→快照与售后→分包与话术→查询端上线。每阶段交付自动化测试全绿 + 真实数据验收 + git 留痕。

上线不是终点：部署阿里云 ECS（systemd 自启 + 每日凌晨备份 + 部署全程留痕），群友用昵称就能查自己的订单。运营数据正在积累中。

如果重来

① 先拿真实样例，再定导入规则。

收集表解析和图片匹配的规则，我用模拟数据先做了「通用版」，真实收集表到货后仍需校准。如果重来，第一件事是拿一份真实导出样例把规则钉死。

② 产品文案要站在用户视角。

台账卡片曾写「国外发货」，用户一眼看出与「未下单」矛盾——它的本意是「商品来源海外」。改名为「海外商品」才消除歧义：标签要描述事实，不能造成状态误解。

③ 被使用推翻的方案是资产。

「图片 zip 自动匹配 + AI 视觉核对」被真实使用一天内否决并重构为人工核对。快速上线、被真实使用推翻、再重构，比闭门打磨完美方案更接近真相。
