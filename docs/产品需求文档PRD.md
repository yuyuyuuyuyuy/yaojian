## 第一章 产品定义

**一句话**：药鉴 = **能核对原文的私人学习知识库**——把课件、笔记装进自己电脑，问什么答什么，每个答案都能点开原文逐字核对；背得会、考得上。

**主标语**：「答有所据，学有所成」 ｜ 副标语：「背得会 · 考得上的药学学习助手」

**产品形态**：桌面 APP（Windows，Mac 规划中）；数据全部本机存储；问答/识别时仅把检索片段发送至阿里云百炼 API（按量付费）。

**目标用户**（见需求调研文档第二章）：
| 用户群 | 定位 | 核心 JTBD |
|---|---|---|
| C 群 考研药学考生 | **重点群** | 把零散、重复、难检索的考研资料变成随时可查、可背、可考的知识体系 |
| A 群 在校生（课程学习/期末备考/QC 实习衔接 3 细分） | 主力群 | 在资料堆里快速找到可靠答案；把零散资料变成能背能刷的复习材料 |
| B 群 药企 QC 检验员 | 次级观察群（降级） | 暂缓，未来企业版形态再评估 |

**核心差异点**（四维空白象限，见市场与竞品分析 2.3）：**可信引用（逐句核对）× 学习闭环（背得会/考得上）× 垂直药学语料 × 零门槛产品化**——市场上无竞品同时占据。

## 第二章 功能规格（用户故事 + 验收标准）

> 每条功能 = 用户故事（作为谁，想做什么，以便得到什么价值）+ 可测试的验收标准 + 对应假设。开发顺序按需求分级：P0 → P1 → P2。

### P0 信任根基（缺一不可）

**F0 会话历史**
- 用户故事：作为学生，我想回看之前问过的问题与回答，以便复习巩固、导出过程记录。
- 验收：①按时间倒序列出全部会话（标题/时间/知识库范围；**标题自动取首问前 N 字，可手动改名**）；②点击载入历史问答继续对话；③可删除单会话；④对话可导出带引用（与 F3 的导出能力共享）。
- 依据：S6 评审补漏（回看复习是学生基本需求；S11 测试的过程证据依赖此功能）。

**F1 资料入库**
- 用户故事：作为学生，我想把课件/讲义/笔记（txt/pdf/docx/pptx）导入知识库，以便把分散的资料集中起来统一检索。
- 验收：①各格式导入成功且内容可检索；②PPT 图片型页面自动识别文字（文本页零费用）；③扫描版 PDF 支持整本 OCR 页码级入库；④**增量索引三行为：未变文件跳过（不重复花费）、变更文件重新索引、已删文件移出索引——索引与资料目录始终一致**；⑤导入失败的文件有明确清单与原因；⑥**误删保护：知识库删除需二次确认，确认弹窗明示后果（「将删除 N 个文档、N 个块，不可恢复」），并提示可先导出备份（联动 F13）**。
- 假设：P4/H6（PPT 导入意愿）。

**F2 多知识库问答**
- 用户故事：作为学生，我想按课程建多个知识库并任选单个/多个/全部来提问，以便期末跨课程整合复习。
- 验收：①单选/多选/全部三种范围均正常检索与回答；②回答引用标注所属库名；③流式输出；④多轮追问（含指代）正确（A7b）；⑤**多轮上下文采用有界窗口**（携带最近 N 轮历史+必要时摘要，防成本失控与注意力稀释——Kimi 评测实证 30 轮后模型失忆；窗口外关键信息缺失时提示用户重述）。
- 假设：P1/H3（跨库组合）、A7b 多轮指代改写（决策 13 实证）。

**F3 逐句引用核对**
- 用户故事：作为学生，我想让每个结论带引用编号、点击即展开原文对照，以便敢把答案写进报告、敢背。
- 验收：①每条结论紧跟 [n] 徽章；②点击徽章定位展开对应原文（含库名/文件名/相似度/页码）；③对话可导出 Markdown/Word 且引用内联；④引用编号与原文一一对应不错位；⑤**引用展开面板提供「此引用有问题」反馈按钮**——信任闭环（用户发现出入有出口）+免费质检数据（反馈直达开发者，兼作 F12 保真校验的训练/评测素材）。
- 假设：P2/H1（引用核对建立信任）。

**F4 防幻觉双防线**
- 用户故事：作为学生，我想在资料查不到时被明确告知，以便不把编造的答案当真的用。
- 验收：①检索零命中时不调用大模型、直接返回「资料中未找到相关内容」；②同领域但资料无相关内容时模型诚实拒答；③**弱相关命中（分数接近阈值）时模型不得拼接无关内容作答——须缩小回答范围或明示「仅找到部分相关内容」**；④温度固定 0、提示词铁律（只依据参考资料/只能删减不能增补）；⑤**模型变更管理（CCI 警示）**：任何模型/提示词/阈值变更后，必须重跑金标评测（含拒答题）通过才可发布——模型升级是质量事件而非免费午餐（能力-保守性倒挂：模型越强越不肯拒答）。
- 假设：P5/H2（拒答建立信任）。

### P1 核心价值

**F5 背得会（闭环一期）**
- 用户故事：作为考研/期末复习的学生，我想把知识笔记一键生成问答卡并按记忆曲线复习，以便摆脱 Anki 手工制卡的时间成本。
- 验收：①笔记/知识条目一键生成问答卡（正面问题/背面答案）；②间隔重复调度（艾宾浩斯）；③每张卡片可回溯引用原文（卡片与资料一致性，K12 刚需）；④**防积压机制（K11 教训：Anki 第一痛点是积压恶性循环）——每日复习卡量可设置上限；积压超过阈值时自动降载（当日按「能背多少算多少」调度，不滚雪球），不追加惩罚性堆积**；⑤**背卡前置引导（K11 碎片化教训）——首次进入卡片复习时提示「建议先通过问答/笔记建立整体认知，再背卡巩固」；卡片提供跳回来源笔记的入口（背卡时一键回到完整上下文）**；⑥卡片复习计入有效学习会话（北极星指标）。
- 假设：P9/H10（背诵材料）。

**F6 可定制知识笔记**
- 用户故事：作为学生，我想输入关键词后先看到知识模块分类、勾选我需要的部分再生成，以便得到刚好够用的复习笔记（不多不少）。
- 验收：①关键词检索后展示模块分类供勾选——**模块动态生成**（先检索内容，由模型判断该主题实际具备哪些模块，只展示有内容的模块，不硬凑空模块）；②按勾选模块生成带引用笔记；③格式可选文本/思维导图（大纲渲染树形图）；④可导出 Word/Markdown、可一键存回知识库；⑤**公式导出保真：笔记中公式/化学式导出后不丢失不乱码（Markdown 保留 LaTeX 源码；Word 用 Unicode 数学符号或图片呈现）——验收用含公式的真实笔记测试**。
- 假设：P6/H7（笔记有用度）。

**F7 拍照识字入库**
- 用户故事：作为学生，我想拍一张手写笔记就转成文字并校对后入库，以便纸质笔记也能被检索。
- 验收：①图片（含截图粘贴）识别为文字；②逐张校对修改后可保存入库并参与检索；③识别失败有明确提示不阻塞其他操作；④**识别前明示「图片将发送至云端识别」（隐私知情）**。
- 假设：P3/H4（OCR 校对）。

**F8 考研场景包（重定义：非独立功能，是 F1/F2/F3 的考研场景化封装——用户拍板）**
- 用户故事：作为考研生，我想有一套面向考研资料（真题/讲义/多校课件）的导入引导与考点组织，以便不研究功能说明书也能上手。
- 与 F1/F2/F3 的差异（增量价值）：
  ①**真题/讲义模板化导入引导**：选「考研资料」模式，按「真题/讲义/课件」分类引导导入（底层复用 F1）；
  ②**考点标记**：为真题题目打考点标签，问答时可追问「XX 考点在哪些真题里出现过」（底层复用 F2/F3 的跨库检索与引用定位）。
- 验收：①考研模式引导下完成真题+讲义导入；②按考点提问命中多份真题并定位出处（**考点标记=AI 自动标记+用户可修正——标注结果可见可改，不强迫信任**）；③与普通模式零冲突（同一知识库可在两种模式间切换使用）。
- 假设：P8/H9（考研资料整合）。

### P2 验证后 / 体验优化

**F9 拒答附原因**（G1，成本最低先做）
- 用户故事：作为学生，我想在拒答时知道为什么（知识库没这内容/建议换关键词），以便不认为产品"笨"。
- 验收：①拒答语附带原因与建议（如「知识库中未找到相关内容，可尝试：①换关键词 ②先导入相关课件」）；②**原因与建议由规则模板生成，不调用大模型——零命中保持零成本（与 F4 验收①一致，不矛盾）**；智能建议若需模型生成，另立需求走 P2 验证。
- 依据：RefusalBench 调研（统一话术引发困惑）；H2 联动观察。

**F10 考得上（闭环二期，双重闸门）**
- 用户故事：作为考研生，我想上传目标院校真题让 AI 学风格出模拟题（答案可核对到我的资料），以便按院校风格自测。
- 验收（**上线前必须通过金标出题评测，否则不得发布——立项条件 2**）：①上传真题后生成同题型同难度模拟题（粗粒度，不承诺押题）；②第一版仅客观题（填空/单选/名词解释）；③每题答案可回溯引用原文；④用户主动进入自测模式（AI 不主动弹题）；⑤**自测历史与错题记录**：每次自测的题目/作答留存，错题可重练（自测的价值闭环）；⑥自测结束页内嵌微型问卷（👍/👎，可跳过）；⑦追问历史薄弱点个性化出题（二期增强）；⑧**出题成本闸门：单次自测题量有上限（如 20 题）；生成前显示本次预计费用；超出上限需分批生成**。
- 假设：P10/H11（需求探针）+ 立项条件 3（验证不过则降级）。

**F11 自动评测体系**（G3）
- 用户故事：作为开发者（用户+Claude 协作），我想每次改动自动跑金标评测并对比上次，以便防止能力退化。
- 验收：①金标评测集（单题+多轮+拒答）自动评分（引用溯源/要点覆盖/拒答三关）；②每次运行产出报告并与上次对比（退化/修复清单）；③评测集按 RAGAS 最佳实践逐步扩充至 50+ 条；④**评测一键运行**（脚本化，双击/单命令——运行者是不写代码的项目发起人）；⑤**金标集维护规则：每新增一个功能模块，配套新增金标题（含陷阱题）后才算功能完成**。
- 依据：RAGAS 调研；内部质量成本。

**F12 引用保真校验层**（G2，置信度最低最后做）
- 用户故事：作为开发者，我想自动校验每条引用是否真的支撑该句结论，以便把「57% 引用缺保真」的业界风险挡在门外。
- 验收：NLI/文本匹配校验结论与原文一致性，不一致自动降级或标注；不显著增加问答时延与成本。
- 依据：Correctness≠Faithfulness（57% 缺保真）、AutoAIS/CAQA 调研。

**F13 数据备份与迁移**（评审新增：「本地私有」定位的完整性——数据归用户，就必须让用户带得走）
- 用户故事：作为学生，我想一键导出全量数据并在新电脑上恢复，以便换设备/重装系统后资料与笔记不丢。
- 验收：①一键导出数据包（知识库文档+索引+对话+笔记+卡片，zip 打包）；②新设备导入恢复后功能完整可用；③导出文件不含 API Key 等敏感凭据；④**恢复语义=覆盖式恢复**（当前数据被恢复包替换，执行前有明确确认提示，防误操作丢新数据）。

**F14 用量与费用可见**（评审新增：内置 Key 用量对用户不是黑箱）
- 用户故事：作为学生，我想看到自己本月大概用了多少、额度剩多少，以便额度耗尽前有准备而不是突然报错。
- 验收：①设置页「用量与费用」区块：本月估算用量（按本地事件估算问答/OCR/笔记次数）、费用估算（按官方单价区间）；②内置 Key 额度耗尽前友好提示并引导自填 Key；③余额查询入口（百炼控制台链接，真实余额以控制台为准）。
- 依据：决策 4 待办（百炼限额+用量告警）的正规化。

**F15 意见反馈**（评审新增：S11 用户测试计划明确依赖此功能，PRD 必须承接）
- 用户故事：作为学生，我想在遇到问题或有改进建议时方便地告诉开发者，以便问题被修复、产品更好用。
- 验收：①设置页「💬 意见反馈」入口 → 弹窗（问题描述 textarea）；②三通道：复制内容 / 保存到本机 / 提交 GitHub Issue（预填标题与正文）；③提交过程无需登录、无需跳转新窗口即可完成复制或本地保存。
- 依据：用户测试计划（测试者走设置→意见反馈提交问题）；埋点配套 feedback_submitted 事件。

## 第三章 非目标（明确不做）

| 不做的 | 理由 |
|---|---|
| AI 搜题公共题库、错题本组卷 | 夸克主场，无差异化 |
| AI 写作、AI PPT | WPS 主场，与可信核对定位无关 |
| 通用聊天、生活助手 | 豆包主场 |
| 视频生成、音频讲解 | NotebookLM 招牌功能，差异化纪律（用户拍板） |
| 云端同步、多端移动版 | 与本地私有定位冲突 |
| 社交/社区/打卡 | 与核心价值无关 |
| 押题/命中承诺 | 合规与口碑风险，违背「可信」定位 |
| 单轮口语化改写（A7a） | H5 实验证伪，观察项（S11 观察，有失败案例再立项） |

## 第四章 交付物与运行要求（评审新增：合同须写明交付形态）

| 项 | 规格 |
|---|---|
| 交付形态 | 解压即用 zip（不做安装器——未签名安装器同样触发 SmartScreen，无收益） |
| 运行要求 | Windows 10+；**最低 4GB 内存/2 核 CPU 可运行（推荐 8GB）；几千块规模索引检索响应 <1 秒**；缺 WebView2 运行时启动时弹中文提示+官方下载链接；无 Python 环境要求（自带运行时） |

## 第七章 PM 知识点卡

**卡 1 ｜ PRD 的本质：开发合同**
- 概念：PRD 不是「产品说明书」而是「合同」——开发方（哪怕就是你自己+AI）与需求方之间的交付约定。三要素：范围（做什么/不做什么）、验收（什么算做完）、变更（改需求必须先改文档）。
- 业内做法：功能写「用户故事+验收标准」而非实现细节（实现由开发方决定）；非目标清单与功能清单同等重要（防蔓延）。
- 示例：本 PRD 第三章非目标 8 条——每拒绝一个「顺手加上」的功能（如音频讲解、搜题），都是防止产品变成夸克第二。

**卡 2 ｜ 用户故事格式（As a / I want / So that）**
- 概念：一条需求 =「作为【谁】，我想【做什么】，以便【得到什么价值】」。三段缺一不可——缺「谁」不知道给谁做，缺「价值」不知道为什么要做。
- 业内做法：每条用户故事配验收标准（可测试的完成定义）；验收标准写行为不写实现（「点击徽章展开原文」✓，「用 React 组件实现」✗）。
- 示例：F3 引用核对——「作为学生，我想每个结论带引用编号、点击即展开原文对照，以便敢把答案写进报告」。验收标准全是可观察行为（徽章存在/点击展开/导出内联/不错位）。

**卡 3 ｜ 版本路线图：版本 = 假设的验证单元**
- 概念：每个版本的发布目的是「验证一批假设」，不是「堆一批功能」。版本内容=功能，版本验收=对应假设的判定标准。
- 业内做法：P0 版本验生存假设（用户信不信），P1 版本验价值假设（用户用不用），P2 版本验增长/付费假设。假设不过则下版本止损调整，而不是继续加功能。
- 示例：本 PRD 第五章——V0.1 的验收是金标评测（产品能不能用），V0.2 的验收是 H10/H7/H4/H9 用户测试（用户认不认这些价值），V0.3 的 F10 带双重闸门（探针+出题评测不过就不发）。每个版本都有「不过怎么办」的预案。
