# 药鉴 · 内部验收方案（Dogfooding，S10 产出）

> 版本 1.0 ｜ 2026-09-17 ｜ 0→1 流程 S10（内部验收设计）执行产出
>
> **文档定位**：开发完成（I1~I4）之后、发布给真实用户之前的最后一道关。**Dogfooding（吃自己的狗粮）**：开发者按真实用户的剧本完整使用自己的产品——坐在用户椅子上的人最容易发现「开发者视角看不到的问题」。
>
> **执行时机**：MVP 迭代计划 I4 完成后。本文档是设计方案，执行由发起人+Claude 按清单操作。

---

## 第一章 验收哲学

1. **自己用出问题 ≠ 丢人，发布后被用户发现问题 = 丢信任**。内部验收的每个问题都替产品省下一份用户信任。
2. **按剧本用，不按习惯用**——开发者用自己产品时会本能绕过难用的地方；剧本强制走「用户的路」。
3. **问题全记录，哪怕小到「按钮文字看不懂」**——非程序员发起人的困惑本身就是最真实的用户信号（他是技术小白，与目标用户同频）。
4. **验收的产物是「问题清单+修复记录」，不是「通过报告」**——只挑毛病，不表功。

## 第三章 真实使用场景剧本（Dogfooding 的核心）

> 执行者：发起人（技术小白身份 = 与目标用户同频）。每个剧本按步骤走完，每步记录：①卡住的地方 ②感受 ③截图（如必要）。预计每个剧本 1~2 小时。
>
> **版本适用性**：V0.1 验收=跑剧本 A 全流程 + 剧本 B 的 V0.1 可用步骤（普通模式导入/考点提问/断网/反馈/备份，即 B-1（普通模式）/2/4/5/6）；V0.2 验收=跑完整剧本 B（含考研模式与背得会）。

### 剧本 A：期末备考学生（A 群，A1/A2 细分）

1. 下载解压包，双击启动（**注意记录第一印象**：引导向导每一步是否想跳过、看不懂什么）；
2. 新建知识库「仪器分析」，导入老师发的课件（含 1 个 PPT 和 1 个 PDF）；
3. 等索引进度，去设置页看看「语料统计」确认导入成功；
4. 用口语问法提问：「色谱分析的基本原理是什么」→ 点引用徽章核对原文 → 追问「它分几种方法」；
5. 问一个资料外的问题（如「怎么写好简历」）→ 观察拒答体验；**再问一个资料外但同领域的题（如「药物的降压作用机制是什么」）→ 观察是否同样拒答（双防线第二道：模型铁律拒答）**；
6. 生成一篇知识笔记（勾选需要的模块）→ 导出 Word 打开核对公式；
7. 拍一张手写笔记照片 → OCR → 改一个错字 → 保存入库；
8. 关闭 APP 重开 → 打开历史对话继续问一轮。

### 剧本 B：考研药学考生（C 群）

1. 新建知识库「药学综合」，用考研模式导入 2 份真题（PDF）和 1 份讲义；
2. 按考点提问：「真题中涉及色谱分析的题有哪些」→ 核对引用定位；
3. 生成笔记 → 一键生成问答卡 → 用「背得会」复习 10 张卡（观察间隔调度与防积压提示）；
4. 模拟断网（拔网线）→ 浏览已有卡片与笔记 → 恢复网络 → **再问一题验证问答恢复正常；观察断网期间发起的操作是否有清晰状态提示**；
5. 设置页查看「用量与费用」→ 打开意见反馈写一条测试反馈（验证三通道）；
6. 导出备份数据包 → 在另一台机器恢复 → 核对数据完整。

## 第四章 问题分级与修复流程

| 级别 | 定义 | 处理 |
|---|---|---|
| **P0 阻断发版** | 核心流程走不通（导入失败/问答报错/引用错位/数据丢失）；可信承诺被破坏（编造/拒答失败） | 修复后重跑对应剧本步骤+相关金标题 |
| **P1 必须修复** | 功能可用但体验明显受损（引导看不懂/提示语混乱/按钮无反馈） | 排入修复清单，发版前完成 |
| **观察项** | 偶发、不可复现、或属「个人偏好」 | 记录进问题库，S11 用户测试中重点观察。**判定规则：S11 中 3 名以上测试者独立遇到该问题→升级 P1；无人遇到→观察项关闭（保留记录）**——判定模板写入 S11 数据回收 |

修复闭环：问题清单 → 修复 → **重跑出问题的那一步**（而非整个剧本）→ 记录修复结果 → 汇总发布决策。

## 第六章 PM 知识点卡

**卡 1 ｜ Dogfooding：坐到自己用户的椅子上**
- 概念：开发团队像真实用户一样使用自己的产品。价值不在「找到 bug」而在「找到视角盲区」——开发者知道每个功能的正确用法，用户不知道；开发者看到的永远不是用户看到的。
- 业内做法：用「场景剧本」强制走用户路径（否则会本能绕过难用点）；执行者身份越接近目标用户越好；记录感受而不只是错误。
- 示例：本方案的执行者=发起人（技术小白+药学背景=目标用户同频）——他在引导向导里「看不懂的词」就是真实用户会困惑的点；他的剧本记录表第 3 列「感受/困惑」和「卡住了吗」同等重要。

**卡 2 ｜ 问题分级：不让小问题堵死发布，也不让大问题溜过去**
- 概念：验收发现的问题必须分级处置——全修复会无限延期，全放过会发布灾难。分级标准=「对核心承诺的影响」：P0=核心流程断/信任破，P1=体验伤，观察=不确定。
- 业内做法：P0 修复后重跑对应场景（定点回归，不重跑全部）；观察项带编号进问题库，在真实用户测试中验证是否升级。
- 示例：第四章——「引用错位」是 P0（砸可信招牌），「按钮无反馈」是 P1，「个人偏好类」是观察项。闸门清单里观察项不阻塞发版——否则发版日期会死在最后一个「我觉得这个颜色不好看」上。

**卡 3 ｜ 发布闸门：验收的产出是决策，不是报告**
- 概念：验收结束必须产出一个明确的 GO/NO-GO 决策——清单化闸门（全过才发）比「总结一下情况」强，因为它不留解释空间。
- 业内做法：闸门清单在验收开始前写好（与迭代计划的 Done 定义同理）；每项打勾有据（测试记录/报告存档）；不过就是不过。
- 示例：第五章 7 项闸门全部在开发前定义——「差不多能用了」没有勾可打，所以它不是一个可以绕过闸门的理由。
