## 决策 1：产品形态 — 桌面 APP（2026-09-06）

- **背景**：用户拒绝上云（不花服务器/域名费用、不等 ICP 备案）。
- **结论**：开发桌面 APP「实验室助手」，运行于 Windows + Mac，数据全本机存储，问答直连阿里云百炼 API（按量约 1~2 分/问）。
- **备选**：GitHub 托管网页版（需服务器）；微信小程序（个人主体医疗健康类目过审难 + 强制备案域名）。
- **回退方向**：APP 稳定后若获得企业资质，可把小程序的壳套到同一套后端上。

## 决策 2：技术栈 — Python + pywebview（2026-09-06，用户拍板）

- **备选**：Electron 全 JS（RAG 需重写、中文文档解析弱）；Electron + Python 双引擎（打包最复杂、体积 200~300MB）。
- **选定理由**：一门语言贯穿前后端；复用 Dify 项目全部 RAG 经验；打包路径最短；新手维护最省心。
- **回退方向**：无（框架级决策，不再回退）。

## 决策 3：附加功能范围（2026-09-06，用户拍板）

- **本期做**：笔记导出（Word/Markdown，含引用原文）、多知识库分类（内置 QC 库 + 自建课程库）。
- **二期**：图片 OCR 入库（中文手写/公式识别效果有限、技术最重）。
- **核心自带**：引用原文点击查看、多轮追问、拒答防幻觉、会话历史。

## 决策 4：API Key 策略 — 内置 + 可替换（2026-09-06，用户拍板）

- **结论**：APP 自带一个内置 Key 开箱即用；设置页可换成用户自己的 Key。
- **风险与兜底**：内置 Key 理论上可被从安装包提取盗用 → 百炼控制台设「单 Key 限额 + 用量告警」，内置 Key 只充小额。
- **备选**：仅内置（无替换出口）；用户自填（门槛高、演示体验差）。

## 决策 5：向量存储 — sqlite-vec（2026-09-06，随计划审批）

- **理由**：一个 SQLite 文件装下全部数据（块+向量+文件哈希表），无重型依赖；chromadb 依赖树沉重且 PyInstaller 打包是公认痛点；语料仅几百~几千条。
- **备选/回退**：numpy 暴力检索（接口已抽象，打包遇阻时一天内可换）。
- **已解决的技术坑**：KNN 查询在 JOIN 场景必须用 `k = ?` 显式约束（不能只靠外层 LIMIT）；查询向量必须归一化后 MATCH（否则分数全 0）。

## 决策 6：向量化 — 百炼 text-embedding-v4 API（2026-09-06，随计划审批）

- **理由**：零模型下载（本地 fastembed 需从 HuggingFace 下模型，国内校园网不稳）；embedding 与 LLM 同一供应商、一把 Key；语料小成本可忽略。
- **隐私说明**：问答时检索到的文档片段本就会发给 LLM，本地向量化只解决一半隐私问题；PRD 中明示知情。
- **回退方向**：`embeddings.py` 只暴露 `embed()` 一个接口，将来换本地模型只改一个文件。

## 决策 7：后端 HTTP 层 — Flask（2026-09-06，随计划审批）

- **理由**：纯 Python 小依赖、打包无痛；单机 localhost 用 werkzeug 自带服务器足够；SSE 流式用生成器即可实现。
- **已解决的技术坑**：必须 `Flask(__name__, static_folder=None)` 禁用内置 /static 路由，否则自定义 /static 路由被抢先匹配导致静态资源 404。

## 决策 8：分块策略 — 按行/自然段，不按固定长度（2026-09-06，沿用 Dify 结论）

- **txt**：每行一条完整知识点（语料按此格式编写，对任何切分都健壮）。
- **pdf/docx**：按自然段落，短段合并至 800 字、超长段按句号分号断句。
- **扫描版 PDF**：文字层缺失占比 >70% 时报错提示 OCR 二期。

## 决策 9：防幻觉策略（2026-09-06，沿用 Dify 验证过的铁律）

- 提示词铁律（prompts/qa_system.txt）：只依据参考资料 / 每个结论紧跟 [n] / 查不到说「资料中未找到相关内容」/ 只能删减不能增补 / 温度 0。
- **无命中直接拒答**：检索零命中时不调 LLM，直接返回拒答语（省钱 + 防幻觉）。
- 检索参数：top_k=6、阈值 0.3，设置页可调；召回调试视图可排查「资料里有却答不出」。

## 决策 10：打包 — PyInstaller onedir + zip 分发，不做安装器（2026-09-06，随计划审批）

- **理由**：onefile 启动慢且杀毒误报率显著更高；未签名安装器同样触发 SmartScreen，多一层工具链无收益。
- **用户数据**：全部放 `%APPDATA%\LabAssistant\`（索引可再生，永不作为唯一数据源）。
- **WebView2 缺失**：启动捕获异常弹中文提示框 + 官方 Evergreen 下载链接。
- **已知风险**：PyInstaller 产物可能被杀软误报 → 不用 UPX、依赖精简；极端情况降级为 venv 源码 + bat 启动。

## 决策 11：前端 — 纯静态 HTML/CSS/JS，无构建工具、无 CDN（2026-09-06，随计划审批）

- **理由**：不装 node、不编译，新手可维护；校园网不可靠故不引 CDN，Markdown 渲染用自写迷你渲染器（md.js）。
- **文件上传**：用 `<input type=file multiple>` + `webkitdirectory` 走 HTTP 上传（不依赖 pywebview 原生对话框，浏览器里同样能测）。

## 决策 12：增量索引 — 文件 md5 哈希跳过未变化文件（2026-09-06，随计划审批）

- **实现**：重建时未变化的文件从旧索引整文件复制块（免重新向量化省钱省时）；新增/修改文件才解析+向量化；删除的文件自动消失；最后原子替换索引文件。

## 决策 13：多轮追问改写（2026-09-06，验收发现翻车后补上）

- **问题**：验收第 1 组多轮中「它分几种方法？」检索到紫外分光光度法的内容，模型答错对象。
- **结论**：检索前先让 qwen-plus 把追问改写为独立完整问题（补全「它」「该法」指代），**改写只用于检索**；回答仍用原问题+对话历史。改写失败降级用原问题，不阻塞。
- **理由**：这是经典的多轮 RAG 问题（追问查询太短导致检索跑偏）；Dify 版靠 qwen3-rerank 重排侥幸通过，自研版用改写更省成本、更可控。
- **验证**：改写后 3 组多轮全部通过。

## 决策 17：OCR 引擎 — 百炼云端 qwen-vl 多模态（2026-09-08，用户拍板）

- **背景**：二期「拍照识字入库」。候选三方案：A 百炼云端 qwen-vl；B 本地 RapidOCR；C 云端+本地混合。
- **结论**：**方案 A**。复用现有百炼 Key 与 OpenAI 兼容 client，零安装、打包零负担；中文手写+公式识别能力本地引擎望尘莫及（用户核心场景就是手写笔记）。费用每张约 1~2 分。
- **否决理由**：B 手写识别差、公式不支持、打包增重 100MB+；C 双引擎维护复杂度翻倍，且问答本就需联网，离线 OCR 收益有限。
- **实现**：backend/ocr.py（Pillow EXIF 校正+长边 3000px 等比压缩→base64 data URI）+ `recognize_image` 走 chat.completions 多模态 content 数组；默认 `ocr_model=qwen3-vl-plus`（设置页可换 qwen-vl-max-latest 手写最强 / qwen-vl-ocr-latest 印刷体最省）；**已实测兼容模式 base64 图片可用**。
- **隐私**：OCR 页明示「图片将发送至百炼识别」。

## 决策 19：扫描版 PDF 整本 OCR — sidecar 方案（2026-09-08，用户拍板功能）

- **结论**：OCR 结果写入与原 PDF 同目录的 **「文件名.pdf.ocr.json」**（sidecar，`{"pages":[{page,text}]}`）；增量索引收录 sidecar：每页文本分段、chunk meta 带 `page`、source=原 PDF 名；**有 sidecar 的 pdf 跳过 parse_pdf**（免报错噪音）；files 表记 sidecar 的 md5（sidecar 变化才重新向量化，复用增量索引）。
- **否决方案**：把 OCR 文本拼成一个大 txt 入库——页码混入正文、切块跨页、污染检索文本。
- **实现**：kb.start_pdf_ocr 后台线程（pymupdf 逐页渲染 dpi150 → 并发 2 调 recognize_image、每页 3 次重试 → 写 sidecar → start_ingest）；OCR_STATUS 与 INGEST_STATUS 并列；引用展示「文件·第N页」（chat.py tag + extract_citations page 字段，file 去掉 .ocr.json 后缀）。
- **成本**：每页约 0.5~2 分；200 页约 0.2~1 元、10~20 分钟。中断需重跑（断点续传记三期）。
- **踩坑**：`os.path.splitext("讲义.pdf.ocr.json")[1]` 返回 ".json" 而非 ".ocr.json"——scan_docs 的 extra_exts 必须按**文件名结尾**匹配而非扩展名。

## 决策 21：增量索引两个并发/ID 缺陷修复（2026-09-08，真实手写照片验收揪出）

- **触发场景**：真实手写照片验收时，连续快速保存两张识别结果（ocr-save 各自触发 start_ingest）→ 索引报 `UNIQUE constraint failed: chunks.id`，第一份笔记索引丢失。
- **根因一（并发）**：两个 build_index 同时写同一个 `index.sqlite.tmp`，互踩。修复：kb.py 加每库 `threading.Lock`（INGEST_LOCKS），锁占用期间的调用记 INGEST_PENDING，本轮结束后自动补跑一次（增量幂等，最后跑一次覆盖全部变更）。
- **根因二（id 冲突，v0.1.0 遗留）**：copy_file 保留旧索引的块 id；当一轮重建中"新文件先分配 id 1..N、旧文件随后被复制（旧 id 也是 1..N）"时必然冲突。v0.1.0 没暴露是因为增量场景只有"全复制"没有"新旧混合"。修复：copy_file 在新库里**重新分配连续 id**（vec 行同步重映射）。
- **回归防护**：tests/test_multikb.py 新增第 9 组检查（2 文件建索引 → 加 1 新文件混合重建 → 全量复制重建，共 3 项）。
- **修复后验收**：两照片入库 73 块零报错；检索"道尔顿分压定律/体积功定义式/波义尔定律"全命中；提问"体积功定义式"回答带 3 条引用（含原文与相似度）。

## 决策 22：三期需求拍板（2026-09-09，用户拍板）

三期 4 条需求，逐项拍板如下：

- **①按键分区+高亮**：侧边栏分三组——「知识库」（列表+新建）、「学习工具」（📷拍照识字、📝知识笔记、📄我的笔记，主题色高亮按钮）、「系统」（🕘历史移入、⚙设置）。否决：输入框上方工具栏（占聊天区）、两者结合（重复入口易乱）。
- **②首次引导**：分步向导弹窗（欢迎+Key → 知识库 → 上传资料 → 拍照识字/PPT → 知识笔记 → 完成），可跳过，完成/跳过后不再出现，设置页可重新查看。否决：气泡式提示（分散）、静态图文页（单薄）。
- **③PPT 入库**：混合方案——python-pptx 提取文本层（零 API 费用、秒级）；某页文本过少（<10 字，图片型页）时自动提取该页内嵌图片送 qwen-vl OCR 兜底（约 1~2 分/页）。否决：纯文本提取（图片页无内容）、全页渲染 OCR（需 LibreOffice 外部依赖、慢、贵）。**仅支持 .pptx（老 .ppt 需另存）**。
- **④关键词知识笔记**：完整版——检索（top_k=16）→ LLM 按笔记模板整理（定义/要点/公式/易错，每结论带 [n] 引用）→ 可保存到「我的笔记」（chat.db notes 表，列表查看/删除）、可导出 MD/Word、可一键加入自建知识库（写 txt 入库参与问答）。否决：全库扫描长文（贵慢）、只列原文（不满足需求）。
- **开发顺序**（我定）：P1 PPT 入库 → P2 知识笔记 → P3 侧边栏分区 → P4 首次引导 → P5 收尾打包 v0.3.0。
- **实现取舍**：PPT 图片页 OCR 在索引构建时同步执行（图片页通常少、进度条可见）；OCR 失败降级为该页空文本、不阻塞入库（warning 计数）。笔记生成走非流式（等待可接受，先简后优）。

## 决策 23：三期实施记录（2026-09-09，P1~P4 全部完成验收）

- **P1 PPT 入库（混合方案）**：`parser.parse_pptx` 递归提取文本层（组/表格/图表数据/备注），图片型页（文本<10 字）提取页内图片（含组内嵌套）并发 OCR 兜底（每图 2 次重试，失败降级该页空文本、不阻塞入库）；每页一块 chunk（meta 带 page，超长页分段，短页不过 split_paragraphs 的 8 字过滤）；SUPPORTED_EXTS 加 .pptx，**上传白名单三处硬编码统一改为引用 parser.SUPPORTED_EXTS**（kb.import_files/import_folder/server.upload_docs）。验收 8 项全过（tests/test_ppt.py）。打包 spec collect_all 加 "pptx"。
- **P2 知识笔记（完整版）**：chat.db 加 notes 表；POST /api/notes/generate（top_k=16 → note_system.txt 模板整理 → 带引用）；保存/列表/删除；导出复用 export 模块（export_note_text，md/docx，docx 按 # 层级转标题）；一键入库 note-save 与 ocr-save 共用 `kb.save_text_doc`（文件名清洗+同名加序号，永不覆盖）。验收 14 项全过（tests/test_notes.py）。
- **踩坑（重要，防幻觉双防线的新认知）**：笔记检索本想放宽阈值到 0.25，实测无关关键词「量子色动力学重整化群方程」仍命中 16 条（分数 0.35~0.39，全部来自手写笔记库的物理化学内容）——**embedding 无法区分同领域不同主题（物化 vs 高能物理）**。结论：**阈值保持 0.3（验证过的拒答线），同领域主题漂移由模型铁律拒答兜底**（实测正确输出「资料中未找到相关内容」）。双防线分工明确：阈值挡不同领域（省钱不调 LLM）、模型铁律挡同领域漂移（花 1 分钱但结果正确）。测试固化双防线两个用例。
- **P3 侧边栏分区**：三组——知识库（列表+虚线「＋ 新建知识库」按钮）/ 学习工具（📷拍照识字、📝知识笔记，主题色渐变高亮）/ 系统（🕘历史对话移入、⚙设置）。纯 HTML/CSS 改动，JS 零改动（所有元素 id 保留）。
