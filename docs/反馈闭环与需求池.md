>
> **文档定位**：产品上线后的「意见箱+提案管理」——反馈从三个入口汇集，统一评审决定做/不做/观察。本文档是机制设计，实际运行从 S11 用户测试数据流入开始。

|---|---|---|---|

## 第二章 需求池结构（模板）

> 需求池 = 一张持续维护的表（放 docs/需求池.md，随项目走）。每条反馈一行，状态流转见第三章。

| 字段 | 说明 | 示例 |
|---|---|---|
| ID | 顺序编号（年份-序号） | FB-2026-001 |
| 来源 | 入口①/②/③/④ | ③测试观察 |
| 描述 | 用户原话或问题一句话 | 「导入 PPT 后不知道有没有成功，找不到确认提示」 |
| 严重度 | P0 阻断 / P1 体验 / 观察 | P1 |
| 出现次数 | 同一问题独立用户数（观察项判定规则：≥3 人→升级 P1） | 2 |
| 对应假设/痛点 | 挂靠 P 编号或 H 编号（挂不上的标「新发现」） | P4/H6 |
| 状态 | 候选 → 评审中 → 已排期 → 已拒绝（附理由） | 候选 |
| 评审结论 | 采纳后的处理：进哪个版本/改文档哪条/回复用户什么 | — |

**入库纪律**：①每条反馈必须挂「来源+出现次数」——孤例（1 人 1 次）与群例（≥3 人）处置不同；②「新发现」类（挂不上现有痛点）单独标记——它可能是漏掉的痛点（就像当年 P4 无验证假设一样）；③已拒绝的条目保留并写理由——防止同一条建议被反复提起时重新评审。

## 第三章 评审流程（闭环三拍：收集 → 处理 → 回执）

**第一拍：收集（持续）**
- 三个入口自动落库（反馈写入需求池由发起人/Claude 在每周固定时间归档）；
- GitHub Issue 作为公开反馈的备份渠道，关闭 Issue 时写处理结论。

**第二拍：处理（定期评审，建议每两周一次或每版本发布前）**
- 评审输入：需求池新条目 + 出现次数统计 + 埋点数据佐证；
- 评审方法：复用 S4 的工具——严重度分级（P0/P1/观察）+ KANO 分类（这是什么性质的需求）+ RICE 排序（值不值得现在做）；
- 输出：已排期（进下版本）/ 观察（记录判定条件）/ 拒绝（写理由）。

**第三拍：回执（闭环的关键，缺了等于没闭环）**
- 公开反馈（GitHub Issue）：回复处理结论与版本号；
- 版本更新说明：每版发布时写「本版根据反馈改了什么」（对应用户提的问题编号）——让用户看到自己的话变成了产品改动。

## 第四章 PM 知识点卡

**卡 1 ｜ 反馈闭环：收集→处理→回执，缺一不可**
- 概念：反馈机制的价值不在「收到反馈」而在「反馈者看到结果」。用户提了建议石沉大海，下次不会再提——反馈通道就死了。
- 业内做法：处理结论必须回执（哪怕拒绝也要说为什么拒绝）；回执形式=版本更新说明/GitHub Issue 回复/直接消息。
- 示例：F15 的三通道设计里 GitHub Issue 是公开的——公开回复处理结论既是回执、也是向其他用户展示「这个产品认真听反馈」的信任资产。

**卡 2 ｜ 需求池：孤例与群例的处置不同**
- 概念：需求池管理的核心纪律是「按证据强度处置」——1 个人提 1 次的是「孤例」（先观察），3 个以上独立用户遇到的才是「群例」（值得做）。这是观察项判定规则（决策 41）的延续。
- 业内做法：需求池条目必须记录出现次数；孤例观察、群例评审；「我觉得应该做」不构成入库理由，「N 个用户说 X」才构成。
- 示例：观察项判定模板——S11 中 3 名以上测试者独立遇到同一问题→升级 P1；无人遇到→关闭。需求池的「出现次数」列就是这套规则的数据基础。
